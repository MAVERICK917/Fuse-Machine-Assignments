# AgenticPM OS — Project Description and End-to-End Workflow

## 1. Project Overview

AgenticPM OS is an AI-assisted project management system designed to connect project planning, work-item management, developer assignments, dependency management, and engineering activity from GitHub.

The goal is to create a system where project information is maintained in a structured backend, AI assists in converting project requirements into actionable work items, dependencies organize the implementation sequence, and GitHub data provides visibility into actual engineering activity.

The project is being developed incrementally, with each phase introducing a distinct capability.

The current work described in the development notes focuses on:

1. Establishing the core application and infrastructure.
2. Implementing the Planner Agent.
3. Validating AI-generated plans before saving them.
4. Persisting work items and their dependencies in the database.
5. Integrating GitHub repositories, branches, commits, and pull requests.
6. Testing the system and organizing changes into reviewable GitHub pull requests.

Execution agents, continuous monitoring, and retrieval-augmented generation (RAG) are not part of the current Planner Agent phase unless explicitly added in a subsequent phase.

---

## 2. Main Project Objectives

The main objectives are:

- Provide a structured project management backend.
- Represent projects, teams, developers, sprints, and work items.
- Use an AI Planner Agent to turn project requirements into structured plans.
- Convert the generated plan into persistent work items.
- Define dependencies between work items.
- Prevent invalid dependency relationships, including circular dependencies.
- Track engineering activity using GitHub repository information.
- Synchronize repository, branch, commit, and pull-request data.
- Associate GitHub contributors with developer records.
- Avoid duplicate records during repeated synchronization.
- Provide API endpoints for the application's functionality.
- Test the system using automated tests.
- Keep changes organized into focused commits and pull requests.

The intended result is a foundation for an AI-assisted project management platform in which structured project plans and real engineering activity can eventually be brought together.

The system contains two major workflows:

1. AI-assisted project planning.
2. GitHub engineering activity synchronization.

These workflows use the same project-management backend but serve different purposes.

The Planner Agent creates structured work items and dependencies from planning requests.

# PART A — AI PLANNER AGENT WORKFLOW

## 5. Planner Agent Objective

The Planner Agent converts a project-planning request into a structured plan that the application can validate and persist.

Instead of relying exclusively on manually entered work items, the system uses a language model to assist in breaking a project into smaller, actionable units.

The generated plan must be validated before it is written to the database.

The objective is not simply to generate a natural-language answer. The result must conform to a structured representation that the backend can process.

## 6. Planner Agent Request Flow

### Step 1: Receive the planning request

A client submits a request to the Planner Agent endpoint associated with a project.

The development notes identify the endpoint:

`POST /projects/{id}/plan`

The route receives the project identifier and the planning input defined by the corresponding request schema.

The backend should validate the request and verify that the target project exists.

If required input is missing or the project cannot be found, the API should return an appropriate error.

### Step 2: Prepare the planning context

The application prepares the information required by the Planner Agent.

This may include:

- Project information.
- The user's planning request.
- Constraints supplied by the application.
- The expected output schema.
- Relevant existing records when required by the implementation.

The exact context must be determined from the actual route and agent code. The presence of a project identifier alone does not prove that the agent automatically retrieves every related project record.

### Step 3: Construct the model request

The Planner Agent uses its configured language model and prompt instructions.

The prompt should guide the model to generate a structured project plan instead of an unrestricted prose response.

The expected output should contain the fields required by the application's planning schema.

Depending on the implemented schema, these fields may represent:

- Work-item titles.
- Work-item descriptions.
- Work-item types.
- Priority.
- Estimated effort.
- Developer or role assignments.
- Dependencies between work items.

Only fields supported by the actual schema should be required.

### Step 4: Generate the plan

The language model generates the proposed plan.

The agent should convert the response into the application's expected structured representation.

If the model returns malformed data, missing required fields, or an unsupported structure, the request should fail safely or follow an explicitly implemented recovery strategy.

The system must not assume that an AI-generated plan is valid simply because the model returned a response.

### Step 5: Validate the generated plan

The generated plan passes through the validation logic.

Relevant implementation file:

`src/agent/validator.py`

The validator should check the conditions defined by the application's planning schema and business rules.

Important validation concerns include:

- Required fields are present.
- Field values have the correct types.
- Work-item identifiers or references are valid.
- Dependencies refer to valid work items.
- Dependency relationships do not contain cycles.
- Unsupported or malformed relationships are rejected.
- Invalid plans are not persisted.

The exact checks must be confirmed from the validator implementation.

If validation fails, the application should return a clear error and avoid partially writing an invalid plan.

### Step 6: Prepare database writes

After successful validation, the application passes the structured plan to the plan-writing service.

Relevant file:

`src/services/plan_writer.py`

This service is responsible for translating the generated plan into database records.

It should use the application's existing data models and persistence conventions.

Where a plan includes both work items and their dependencies, the service must ensure that the required records exist before creating relationships between them.

### Step 7: Create work items

The plan-writing service creates the work-item records associated with the plan.

The implementation should respect:

- Required database fields.
- Existing project relationships.
- Valid work-item source values.
- Applicable database constraints.
- The application's developer and assignment conventions.

The development notes mention a schema change that adds `agent` to the `work_item_source` enum and a seeded Planner developer.

These changes support representing AI-generated work within the existing data model.

The precise meaning of each field should be confirmed from the model and migration definitions.

### Step 8: Create dependency relationships

The application creates the dependencies specified by the plan.

Relevant files:

- `src/services/dependency_service.py`
- `src/services/dependency_graph.py`
- `src/api/routes/dependencies.py`

The dependency graph represents relationships between work items.

For example, a backend implementation task may need to be completed before an integration task can begin.

The application should reject dependency relationships that create circular execution requirements.

If task A depends on task B, task B must not indirectly depend on task A.

The system should validate the graph before committing the final set of changes.

### Step 9: Persist the plan safely

The work items and their dependencies should be persisted consistently.

Where the database supports transactions, related writes should be performed in a transaction so that a failure does not leave behind a partially created plan.

The plan-writing service should handle persistence errors and return a useful result to the calling API.

### Step 10: Return the result

The Planner Agent endpoint returns a response indicating the result of the planning operation.

The response format must follow the actual API schema.

A successful response should make it possible for the client to identify the generated work items and understand the result of the operation.

Errors should clearly distinguish invalid input, invalid model output, dependency validation failures, missing projects, and persistence failures where the implementation supports those distinctions.

# PART B — DEPENDENCY MANAGEMENT

## 8. Dependency Graph Objective

A dependency graph represents the ordering constraints between work items.

It allows the application to express which tasks must be completed before other tasks can proceed.

The dependency implementation should provide a shared and consistent way to create, inspect, and validate dependencies.

Relevant files:

- `src/services/dependency_service.py`
- `src/services/dependency_graph.py`
- `src/api/routes/dependencies.py`

## 9. Dependency Management Workflow

### Step 1: Receive a dependency operation

A dependency operation may originate from an API request or from the Planner Agent's generated plan.

### Step 2: Validate the referenced work items

The application checks that the referenced work items exist and that the relationship satisfies the applicable database and business rules.

### Step 3: Check the graph

The dependency service checks whether adding the relationship would produce an invalid graph.

Circular dependencies must be rejected.

For example:

Task A depends on Task B.
Task B depends on Task C.
Task C depends on Task A.

This creates a cycle and should not be accepted when the application requires an acyclic dependency graph.

### Step 4: Save the relationship

If the relationship is valid, the application persists it through the shared service logic.

### Step 5: Return the result

The API reports success or a meaningful validation error.

Dependency validation should be centralized so that the Planner Agent and ordinary dependency endpoints do not implement conflicting rules.

# PART C — GITHUB INTEGRATION WORKFLOW

## 10. GitHub Integration Objective

The GitHub integration brings external repository activity into AgenticPM OS.

The development notes describe synchronizing repository information, branches, commits, and pull requests into the existing database tables.

The integration is intended to make engineering activity available alongside project-management records.

The notes emphasize reusing existing tables rather than creating an entirely separate data model for GitHub.

## 11. GitHub Backfill Synchronization

Backfill synchronization retrieves existing GitHub data and imports it into the application.

The general workflow is:

### Step 1: Configure GitHub credentials

The application reads the GitHub token from configuration.

The development notes mention `GITHUB_TOKEN`.

The token should have only the permissions required for the repositories being accessed.

Real tokens must be stored outside version control.

### Step 2: Receive a synchronization request

A client requests synchronization for a repository through the relevant API endpoint.

The exact endpoint paths and request parameters must be verified from:

- `src/api/routes/github.py`
- `src/api/routes/repositories.py`
- `src/api/schemas/github.py`

### Step 3: Retrieve repository information

The integration retrieves the relevant repository information from GitHub.

The repository is represented in the application's existing repository model.

### Step 4: Retrieve branches

The integration retrieves branches associated with the repository and stores the corresponding records.

Each branch must be associated with the correct local repository record.

### Step 5: Retrieve commits

The integration retrieves the commits covered by its synchronization logic.

The development notes refer to retrieving recent commits per branch.

The actual pagination strategy, historical depth, and rate-limit handling must be verified in the implementation.

### Step 6: Retrieve pull requests

The integration retrieves the pull requests covered by its synchronization logic.

The local records should retain the relevant external identifiers and repository relationships.

### Step 7: Resolve authors

GitHub commit and pull-request authors need to be associated with developer records.

The development notes describe a resolution strategy that checks GitHub external identity first and then email.

If neither matches, the integration may create a developer record.

This behavior is important because the application model requires an author relationship for the relevant records.

The implementation must handle missing or inconsistent identity information carefully to avoid incorrect matches.

### Step 8: Persist synchronized records

The integration writes the retrieved records into the existing database tables.

The notes identify existing concepts such as:

- Repositories.
- Branches.
- Commits.
- Pull requests.
- Developers.
- External identities.

### Step 9: Avoid duplicates

Synchronization must be safe to repeat.

The notes describe using upsert-style persistence and existing uniqueness constraints involving repository, source, and external identifiers.

When the same synchronization is run again, existing records should be updated or reused rather than duplicated.

The actual uniqueness constraints and upsert behavior must be verified against the models, migrations, and service code.

### Step 10: Return synchronization results

The API should report the outcome of the operation using the implemented response schema.

Useful information may include the repository synchronized, the categories of records processed, and any errors encountered.

The response should not claim successful synchronization of records that were not actually retrieved or saved.

## 12. GitHub Webhook Workflow

The development notes discuss webhook-based updates for incremental synchronization.

Webhook functionality must be verified against the actual implementation before being treated as complete.

Where implemented, the logical workflow is:

1. GitHub sends an event to the configured webhook endpoint.
2. The application receives the request.
3. The application verifies the webhook signature using the configured secret.
4. Invalid signatures are rejected.
5. The application identifies the event type.
6. The integration processes supported events, such as push or pull-request updates.
7. Relevant local records are inserted or updated.
8. The application returns an appropriate HTTP response.

The notes mention `GITHUB_WEBHOOK_SECRET`.

Webhook signature verification is essential. The application must not blindly trust incoming webhook requests.

The integration should also handle duplicate event deliveries safely.

If webhook handling is not present in the current code, it should be treated as planned work rather than a completed capability.

# PART D — DATA CONSISTENCY AND ERROR HANDLING

## 14. Data Consistency

The system combines AI-generated planning data with externally retrieved GitHub information.

Both sources must be handled carefully.

The application should enforce:

- Database constraints.
- Valid foreign-key relationships.
- Valid dependency relationships.
- Stable external identifiers.
- Duplicate-safe synchronization.
- Consistent developer resolution.
- Transactional persistence where appropriate.
- Clear error reporting.

The Planner Agent and GitHub integration should use shared persistence services when they operate on the same underlying entities.

## 15. Error Handling

Important failure scenarios include:

### Planner Agent errors

- Missing project.
- Invalid request.
- Language-model request failure.
- Malformed model output.
- Missing required work-item fields.
- Invalid dependency references.
- Circular dependency.
- Database persistence failure.

### GitHub integration errors

- Missing or invalid credentials.
- Repository access denied.
- Repository not found.
- GitHub API errors.
- Rate limits.
- Pagination failures.
- Incomplete external identity information.
- Duplicate events.
- Invalid webhook signature.
- Database persistence failure.

Errors should be handled at appropriate boundaries.

The API should return useful client-facing messages without exposing secrets, access tokens, stack traces, or other sensitive internal details.
